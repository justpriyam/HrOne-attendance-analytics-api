# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `health()` L72-74 | Returns `{"status": "ok"}` without verifying MongoDB connectivity. | A failing database still appears healthy to readiness probes. The runner polls `/health` before testing. | Added `client.admin.command("ping")` and return 503 on failure. |
| 2 | `create_employee()` L78-85 | `find_one()` then `insert_one()` — TOCTOU race condition. | Two concurrent `POST /employees` with the same `emp_code` can both succeed. Under load, duplicates are created. | Rely on the unique index on `emp_code` and catch `DuplicateKeyError` for 409. Removed the `find_one` check entirely. |
| 3 | `list_employees()` L93 | `skip = page * page_size` — off-by-one. Pages are 1-indexed, so page 1 skips the first page of results. | `GET /employees?page=1` returns what should be page 2; page 1's items are unreachable. | Changed to `skip = (page - 1) * page_size`. |
| 4 | `list_employees()` L94 | `count_documents({})` ignores the active `department` filter. | Total count is wrong when a department filter is applied; pagination metadata is misleading. | Changed to `count_documents(q)` using the same query object. |
| 5 | `list_employees()` L95 | No `.sort()` — MongoDB does not guarantee document order without one. | Paginated results can return duplicates or miss items across pages. | Added `.sort("emp_code", ASCENDING)` for deterministic pagination as specified in the contract. |
| 6 | `punch_in()` L102 | `datetime.fromtimestamp(body.punched_at / 1000)` uses the server's local timezone. | On a server in UTC-5, an IST date calculation would be wrong. Attendance dates depend on the deployment environment. | All timestamps are stored as UTC-aware datetimes. Conversion uses `datetime.fromtimestamp(..., tz=timezone.utc)` and explicit IST offset. |
| 7 | `punch_in()` L102 | `punched_at` is divided by 1000 assuming milliseconds but no validation that it actually is milliseconds. Values below `100000000000` (which look like seconds) are silently accepted. | A client sending seconds instead of milliseconds produces a date in 1970. | Added validation: reject values < 100000000000 or > 4102444800000 with 422. |
| 8 | `punch_in()` L103 | `ts.date().isoformat()` uses the server-local date, not the IST date. | On a UTC server, a punch at 23:00 IST (17:30 UTC) gets the wrong calendar date. | Attendance date is derived by converting to IST explicitly and handling overnight shifts per R1. |
| 9 | `punch_in()` L104-105 | `find_one()` before `insert_one()` — same TOCTOU race as employee creation. | Two concurrent punch-ins for the same employee and date can both create a record. | Unique compound index on `(emp_code, date)` + catch `DuplicateKeyError`. |
| 10 | `compute_late_minutes()` L37 | `minutes > 10` uses strict greater-than, but the condition should be "strictly more than 10:00 after shift_start" (R2). The implementation computes minutes from `punch_in - shift_start` and checks `> 10`, which happens to be correct for integer minutes but ignores seconds. | Exactly 10 minutes and 1 second is handled differently depending on whether you truncate. With the floor-based approach, `601 seconds // 60 = 10`, so `10 > 10` is false — the employee escapes being late by 1 second. | Changed to compare in seconds: `diff_seconds > grace_seconds` (600 seconds). When late, `late_minutes = floor(diff_seconds / 60)`. |
| 11 | `compute_late_minutes()` L35 | `punch_in.replace(hour=h, minute=m)` assumes `punch_in` is in the shift's timezone. It is not — `punch_in` is UTC in the starter. | Late calculation is wrong by 5:30 hours on every single request. | Build `shift_start_ist` as an IST datetime on the attendance date, then compare against the UTC punch-in. |
| 12 | `compute_work_hours()` L41 | `round(..., 2)` uses Python's banker's rounding (ROUND_HALF_EVEN). | `round(8.845, 2)` gives `8.84` instead of the required `8.85`. Can be triggered by any shift duration that ends in a .5 fractional digit. | Used `Decimal.quantize(Decimal('0.01'), rounding=ROUND_HALF_UP)`. |
| 13 | `compute_overtime()` L44-47 | `max(0, int((punch_out - end).total_seconds() / 60))` counts any positive overtime. | 15 minutes after shift end is reported as overtime even though R3 requires a minimum of 30 minutes. | Check `minutes >= 30` before counting overtime; return 0 otherwise. |
| 14 | `compute_overtime()` L46 | `datetime.fromisoformat(date_str).replace(hour=h, minute=m, tzinfo=IST)` constructs the shift end time from the date string but doesn't handle overnight shifts where the shift end falls on the next calendar day. | For a 22:00-06:00 shift, the shift end of 06:00 is computed as 06:00 on the same day instead of the next day, so overtime is wildly wrong. | Added `if _is_overnight_shift(): shift_end_ist += timedelta(days=1)`. |
| 15 | `EmployeeIn` model L53-61 | Model uses `email` and `joined_on` fields correctly, but `punched_at` in `PunchInIn` (L65) is typed as `Optional[int]` with no validation. Seconds-looking values are accepted. | Any integer is silently accepted as a timestamp. | Added `_validate_epoch_ms()` to reject values outside the valid millisecond range. |
| 16 | Missing entirely | No `POST /attendance/punch-out` endpoint. | Employees can punch in but never punch out. Half the attendance lifecycle is missing. | Implemented full punch-out with atomic `update_one` using `{"punch_out": None}` guard for concurrency. |
| 17 | Missing entirely | No `PATCH /attendance/{emp_code}/{date}` regularization endpoint. | Manual corrections are impossible; no audit trail. | Implemented with `$push` for history, before/after change tracking, derived field recomputation. |
| 18 | Missing entirely | No analytics endpoints (`/analytics/employees/{emp_code}/monthly`, `/analytics/departments/summary`, `/analytics/leaderboard/late`, `/analytics/departments/{department}/trend`). | 30% of evaluation weight. | Implemented all four with MongoDB aggregation pipelines. |
| 19 | Missing entirely | No `GET /admin/explain/{endpoint}` endpoint. | Cannot verify index usage or query performance. | Implemented with `executionStats` explain for each endpoint's main query/pipeline. |
| 20 | Missing entirely | No indexes created at startup. | Every query is a `COLLSCAN` — fails the grader's performance check on 100k records. | Created indexes in the `lifespan` handler: unique `emp_code`, compound unique `(emp_code, date)`, `department`, `date`, `status`. |
| 21 | Missing entirely | No lifespan management — the MongoDB client is created at module level with no cleanup. | Not critical for correctness, but prevents graceful shutdown. | Used FastAPI's `lifespan` async context manager. |
| 22 | `list_attendance()` L144-146 | Loads ALL matching documents into memory, sorts in Python, then paginates. | On 100k records, this loads the entire collection into memory and is extremely slow. | Changed to `find(q).sort(...).skip(...).limit(...)` with database-side pagination and sorting. |
| 23 | Missing | Response format uses `"items"` key but the fields inside attendance records don't match the contract — no epoch-ms conversion, no `history` field, fields like `id` are non-standard. | Grader gets wrong field names and types. | `_record_to_response()` converts every document to the exact contract format with epoch-ms timestamps. |

## Not a defect

| Where | Why it looks suspicious | Why it is correct |
|---|---|---|
| `IST = timezone(timedelta(hours=5, minutes=30))` L25 | A hardcoded timezone offset looks fragile. | IST is a fixed UTC+05:30 offset with no DST. This is the correct way to represent it. |
| `pymongo` (sync) instead of `motor` (async) | FastAPI is async-capable, so sync calls seem wrong. | The starter uses sync pymongo and the spec says "put all code in `app/main.py`". FastAPI runs sync endpoints in a threadpool. For this assignment scale, sync pymongo is fine and simpler. |
